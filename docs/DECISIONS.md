# DECISIONS · 技术与产品决策

## 2026-10-29 · 转向牧场题材《牧云》

**背景**：校园地图复刻的视觉效果不达预期。根因不是美术工作量，而是
"用 480×270 像素去复刻真实 GIS 数据"本身信息密度错配：22 栋真实建筑每栋只有
30×20 像素，画不出屋顶、门头与材质，只能得到色块。

**决策**：

1. **保留引擎，换内容层。** 3007 行代码中 1971 行（65.5%）是通用引擎，
   只有 1004 行是校园内容。转向成本因此远低于重写。
2. **不做写实 3D。** 技术栈与审美风险都在像素侧，3D 会重演同一次失败。
3. **先做 D 版（13 周一局、事件卡、5 结局），再做 A 版（连续经营）。**
   D 是 A 的可发布切片：共用 `sim` 内核、事件系统与美术管线。
4. **混合式场景。** 牧场可走动，作为"活的仪表盘"；决策通过点击建筑/动物
   打开 DOM 面板完成，不强迫玩家走到位置才能操作。
5. **冷峻高原视觉。** 钴蓝天空、草黄、墨黑牦牛、青白雪；32 色有限色板。
6. **智慧畜牧 = 买信息，不是买加成。** 项圈、疫情预警、草场监测都要花钱，
   效果是提前看到风险。这是差异化机制，也是答辩的核心论点。

**备份**：校园版完整保留在 tag `campus-v0.1`。

## 2026-10-27 · 采用 Phaser 2D，而不是 Three.js 3D

Phaser 2D 在 480×270 像素画布上可以用程序化素材快速迭代；Three.js 的
像素化 3D 管线（低分辨率 RenderTarget + 32 色量化）虽然视觉独特，但建模、
导出、光照、性能四道工序都更重，不适合单人 15 周周期。

## 2026-10-27 · 程序化像素素材，不用外部图库

所有瓦片、角色、树、建筑均由 `tools/*.mjs` 用自研 PNG 编码器 + Canvas 原语生成。
好处：零第三方依赖、确定性可重跑、无版权风险、改色板即改全局风格。
代价：每个新素材要写绘制代码，且当前存在三份重复的 PNG/Canvas 实现。

**后续修正**：Phase 1 起把公共部分抽到 `tools/lib/pixel.mjs`，色板集中到
`tools/theme/ranch.json`。

## 2026-10-27 · HTML/CSS UI 而不是 Phaser UIScene

对话框、HUD、模态框、摇杆全部是 DOM 叠加。好处：中文排版、滚动、无障碍、
响应式都免费；调试用 DevTools 即可。坏处：DOM 与 Phaser 的层级和输入焦点
需要手动协调（用 `ui.isBlocking()` 统一判断）。

## 2026-10-27 · 数据驱动的交互与存档

触发器、对话、建筑全部用 JSON 描述，新增内容不改代码。
存档统一走 `SaveSystem`，schema 带 `version`，迁移必须有单测。

## 2026-10-27 · 修复地图时放弃"全量 footprint"

把 128 个真实建筑 footprint 全铺进 160×120 地图后完全不可读，最终回退到
22 栋核心建筑。**教训**：先定"可玩密度"，再铺量。牧场地图同样适用。
